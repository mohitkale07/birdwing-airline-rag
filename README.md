# Birdwing Airlines RAG Demo

A learning project that ingests three fictional, AI-generated Birdwing Airlines
PDFs and answers policy questions using hybrid retrieval, reranking, and an LLM.
The sample documents are fictional and are not real airline policies.

## Requirements

- Python 3.11
- A NVIDIA API key to generate answers

The sample PDFs are included in `data/raw`. Ingestion downloads/loads the
embedding models used by Docling, Sentence Transformers, and FastEmbed; the
first run may take some time and require an internet connection.

## Setup on Windows

From the project root, run:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
Copy-Item .env.example .env
```

The API allows browser requests from `http://localhost:3000` and
`http://127.0.0.1:3000` by default, with credentials enabled for the auth
cookie. For another frontend origin, set `CORS_ORIGINS` in `.env` to a JSON
array of exact origins (including scheme and port), then restart the API:

```dotenv
CORS_ORIGINS=["http://localhost:3000","https://app.example.com"]
```

Frontend requests that need the auth cookie must include credentials, for
example `fetch(url, { credentials: "include" })`. Do not use `*` as an allowed
origin when credentials are enabled.

Set your database, mail, Google OAuth, and NVIDIA credentials in `.env`. Add
`http://127.0.0.1:8000/api/v1/auth/google/callback` as an authorized Google
redirect URI. Set `AUTH_COOKIE_SECURE=false` for local HTTP development; use
HTTPS and secure cookies when deployed. Never commit `.env` or share secrets.

## Ingest and build the local vector store

Run the ingestion steps in order:

```powershell
python -m src.ingestion.run_pipeline
python -m src.vector_store.ingest_qdrant_hybrid
```

The first command reads all PDFs in `data/raw`, chunks them, creates dense
embeddings, and writes `data/processed/chunks.json` and
`data/processed/embeddings.npy`. Each PDF must have an entry in
`DOCUMENT_ACCESS` in `src/ingestion/run_pipeline.py`; this is where its source
category and allowed roles are configured.

The second command creates the local hybrid Qdrant collection in
`data/qdrant_hybrid`. **It recreates that collection**, so rerunning it replaces
the current collection contents.

Generated chunks, embeddings, and local vector database files are ignored by
Git. They are regenerated by running these steps after cloning.

## Ask a question

```powershell
python -m src.generation.answer_question
```

Choose a demo role and enter a question when prompted. The role prompt is only
for local experimentation; it is not authentication. Do not expose this
role-selection flow as a public API until roles are derived from a trusted,
authenticated user identity.

For each question, the NVIDIA-hosted LLM generates four alternate search
queries. The original question and its variants are each searched in the
role-filtered hybrid Qdrant collection. Results are deduplicated and combined
with reciprocal rank fusion, then reranked against the original question using
the cross-encoder.

## Database and authentication layer

The project has SQLAlchemy models for users, authentication accounts, and email
verification tokens, with Alembic migrations. The API supports email/password
registration and login, email verification, and Google OAuth:

- `GET /api/v1/auth/google/login` starts Google sign-in.
- `GET /api/v1/auth/google/callback` completes sign-in and sets the auth cookie.
- `POST /api/v1/auth/google/link` starts linking Google to the authenticated
  account.
- `DELETE /api/v1/auth/google/unlink` removes Google when another sign-in method
  is connected.
- `POST /api/v1/chat/stream` accepts a JSON `ChatRequest` and streams a policy
  answer as server-sent events. A signed-in user can send
  `{"conversation_id": null, "text": "..."}` to start a conversation or send
  the returned `conversation_id` to continue it. The user and completed
  assistant messages are saved to the database. Anonymous requests can ask
  public-policy questions, but are not saved and cannot continue a saved
  conversation.

The chat stream begins with a `start` event containing the conversation and
user-message IDs when saved, emits answer `token` events, and ends with a `done`
event containing the assistant-message ID and source references. If generation
or saving fails, it emits an `error` event. Conversation history is included
when answering follow-up messages.

Other chat endpoints, which require authentication and only return or modify
the current user's conversations:

- `GET /api/v1/chat/conversations?limit=20&offset=0` lists sidebar conversations
  with message counts and the latest message preview. Set `include_archived=true`
  to include archived conversations.
- `GET /api/v1/chat/conversations/{conversation_id}?limit=50&offset=0` returns
  a conversation and a page of its messages.
- `PATCH /api/v1/chat/conversations/{conversation_id}` updates `title` and/or
  `is_archived`.
- `DELETE /api/v1/chat/conversations/{conversation_id}` deletes the conversation
  and its messages.

Admin-only endpoints:

- `GET /api/v1/admin/users?limit=20&offset=0&search=...` lists users and their
  conversation/message counts.
- `PATCH /api/v1/admin/users/{user_id}/restriction` accepts
  `{"is_restricted": true}` or `false`. An admin cannot restrict their own
  account or the last active admin.
- `GET /api/v1/admin/metrics` returns aggregate user, conversation, and message
  counts.

Example request:

```json
{
  "conversation_id": null,
  "text": "What is the annual leave policy?"
}
```

The `done` event includes `conversation_id`, `user_message_id`,
`assistant_message_id`, and `sources`; use its conversation ID on subsequent
requests in the same chat.

Apply database migrations before using saved chat history:

```powershell
alembic upgrade head
```

Google accounts are linked to an existing account only when Google returns a
verified matching email. Registering an email/password credential for an
existing Google account requires confirming the email link before the password
credential is added.

For local development, start PostgreSQL and create the database named
`birdwing_rag`. Copy `.env.example` to `.env` and set your database URL and API
key. Never commit `.env` or use example secrets in a deployed app. Create the
tables and insert demo rows with:

```powershell
alembic upgrade head
python -m src.db.seed
```

The seed command adds three demo users, a synthetic Google account for each,
and a hashed placeholder verification token for the unverified user. It is
safe to rerun: existing rows are left as-is, and only missing rows are added.
These are test records, not usable Google identities or verification links.
Do not use the demo seed in a production database.

### Adding more seed data

Add your sample values to `DEMO_USERS` and update `seed_reference_data` in
`src/db/seeders/reference_data.py`. For a new table:

1. Import its SQLAlchemy model and add a seeded row after its parent row has
   been created. This matters when the table has a foreign key.
2. Choose a stable unique value (such as an email or token hash), query for it
   first, and insert only when it does not exist. This makes reruns safe.
3. Keep secrets out of seed files. Store hashes where the model expects hashes;
   never add a real password or raw verification token.
4. Add a counter to the returned `created` dictionary and to the completion
   message in `src/db/seed.py`.
5. Run `python -m src.db.seed` again and check that the second run reports zero
   rows added.

## Evaluation

Evaluation scripts and test cases are in `src/evaluation` and
`data/evaluation`. The checked-in scored reports are snapshots from an earlier
Flykite-named sample corpus. Review/update the expected document names, facts,
and pages in the test cases before treating those scores as validation for the
included Birdwing PDFs.

## Project limitations

This is a learning/demo project, not a production service. It does not provide
rate limiting or production-grade monitoring.
